# Analytics rollout

Implemented admin reports: registrations, event creation, organizer adoption, ticket sales, revenue (including tax collected), website traffic, user engagement, and checkout conversion. Open Analytics in the admin app; the Revenue navigation opens the same reporting interface with Revenue selected.

## Deployment

1. For automatic setup, take a database snapshot and deploy with `DB_SYNCHRONIZE=true`. TypeORM creates the analytics table, nullable checkout attribution columns and all nine analytics/report indexes before the API starts accepting requests. No manual SQL is required for this path. Synchronization reconciles every registered entity, including other existing local backend changes; it is not restricted to analytics. The database user needs schema-altering privileges. After a successful rollout, setting `DB_SYNCHRONIZE=false` prevents future deployments from automatically changing the schema. If synchronization is disabled from the outset, apply `sql/20261014-analytics.sql` and any other pending schema changes before deploying.
2. Deploy the API and admin app together. Reports read existing data immediately. No seed/reset scripts are needed for this feature.
3. To collect new website activity, set backend `ANALYTICS_TRACKING_ENABLED=true` and `ANALYTICS_ALLOWED_ORIGINS` to a comma-separated list of exact frontend origins (no trailing slash).
4. Set web `NEXT_PUBLIC_ANALYTICS_ENABLED=true` and rebuild/deploy the public site. Keep its existing `NEXT_PUBLIC_API_URL` pointing at the deployed API. Collection is disabled by default so an incomplete rollout does not silently collect data.
5. Visit a public event and select a ticket. Verify POST `/api/analytics/events` returns `{accepted:true}`. Confirm `analytics_events` has page views and ticket-selection events. When a checkout is created, its order should have `analytics_session_id` and `analytics_visitor_id`. Confirmed purchases are derived from that order's backend `paid_at` and status, not client telemetry.

Production data and environment files have not been changed by this implementation.

## Report API and definitions

Authenticated GET `/api/analytics/reports/:report` accepts required `start` and `end` (YYYY-MM-DD inclusive), optional `groupBy=day|week|month`, `organizationId` and `eventId`. Maximum range is 366 days. Reporting days use UTC, weeks start Monday, and partial buckets include only dates inside the filter. The response has columns, zero-filled buckets, independently calculated totals and the immediately preceding equal-length period. GET the same path with `/export` for a CSV containing both periods and their filter metadata. CSV opens in Excel; native XLSX export is not included in this phase.

- `registrations`: all accounts by creation date, including unverified accounts. Platform administrators only; organization/event filters are rejected because registrations are not attributable to events.
- `event-creation`: events by creation date, regardless of current status.
- `organizer-adoption`: organizations of type `organization`, excluding vendor/influencer accounts. New organizers are counted by organization creation date. Active means creating an event or receiving a confirmed order during the period. Published means currently published events created in the period, not historical publication transitions. Distinct totals are calculated across the whole period, not summed from daily counts.
- `ticket-sales`: confirmed orders by `paid_at`, including orders later refunded. Ticket quantities come from ticket order items, so merchandise does not inflate ticket counts. Order counts may include merchandise-only checkouts. Free/paid-price counts use ticket unit prices; order-level discounts do not reclassify tickets. Net unrefunded ticket quantities are not inferred from monetary refunds.
- `revenue`: separate currencies. Gross checkout sales include tickets and merchandise, using the saved gross subtotal when available. Buyer payments, tax collected, platform fees and processing fees use saved order amounts. Tax collected is gross tax on confirmed orders before refunds, by paid date and currency. It is not added to platform revenue and is not a statement of tax remittance; tax refund allocations are not inferred. Only succeeded refunds with `completed_at` are counted, on their completion date, even if the sale was earlier. Estimated platform revenue subtracts proportional platform-fee refund allocations, not the entire refund. This is not reconciled accounting profit: actual processor costs, fee reversals and disputes require further provider/ledger reconciliation.

The API allows administrators platform-wide access. Other authenticated users must select an organization they own or actively belong to; event filters must belong to that organization. These same checks execute before CSV exports. The new report UI is in the admin application; organizer report screens are not added in this phase, but scoped report endpoints are available.

## Tracking foundation

Collection covers home, discovery (`/discover`), public event listings/details and ticket selection, plus public information, blog, vendor and organizer profile pages. Authentication, account, organizer dashboard and payment/result screens remain excluded. Only coarse page categories are recorded. Engagement is visible-page time while activity was detected within the last minute, sent in small intervals. Ticket selection and checkout starts are deduplicated within a browser tab/session/event. New checkout orders retain anonymous session and visitor IDs so a future funnel can count distinct sessions and use backend-confirmed payments.

Visitor IDs rotate after 90 days. Sessions expire after 30 minutes without recorded activity. Browser storage restrictions, failed network requests and disabled tracking never block checkout. Do Not Track, Global Privacy Control and localStorage `vs_analytics_opt_out=true` suppress collection and attribution. Only page categories, event IDs, coarse source labels and anonymous IDs are sent; URL paths, query parameters, access tokens, buyer details, and full referrer URLs are not collected. This does not add a consent-management UI.

Raw events are deleted after 90 days by a daily UTC job. Order attribution columns follow existing transaction retention. The collector validates an allowlisted payload and origin, deduplicates event IDs, disallows purchase events, and limits requests per network address in each API instance. Configure shared edge rate limiting for a multi-instance deployment; do not blindly trust forwarded IP headers. Browser tracking remains best-effort and can be blocked or spoofed, so it must not determine financial totals.

Tracking report endpoints use the same UTC date filters, grouping, comparisons, CSV and organization access rules:

- `website-traffic`: unique browser visitors, distinct visitor/session pairs, page views, and pages per session. Counts come from `page_view` events only. Distinct totals cover the whole selected period; daily unique counts are not added together.
- `user-engagement`: unique visitors with any tracked activity; returning visitors with an earlier different retained session in the same scope; visitors with positive engagement; page views; total engaged seconds; average engaged seconds across all active sessions; and returning visitor percentage. One visitor may first appear and return within the selected period. The earliest session retained in this scope provides only an observed baseline, not an account creation date.
- `checkout-conversion`: group event-linked signals into one visitor/session/event journey and assign the journey to its first retained page-view/selection/start date. Starts and selections count only within 24 hours of first activity. Payments must match the journey's visitor ID, session ID and event, and occur from checkout start through the following 24 hours. A refunded confirmed order or free order still counts as completion; retries count once. Completion may occur after the reporting period ends. New unfinished starts are pending; those beyond 24 hours without completion are not converted. Conversion percentage is completed journeys divided by started journeys (including pending). Browser signals are observed stages and can have gaps; they are not guaranteed to form a strictly decreasing funnel. Orders without tracking identifiers are not attributed.

Returning history and funnel cohorts are based only on retained observations. Each tracking report supplies scoped earliest/latest retained activity, the retention cutoff and generation time. These are not proof of an uninterrupted collection period. The UI flags missing/limited tracking and potentially incomplete comparisons. Rates with no denominator are null and display as unavailable. CSV includes definitions, units, tracking coverage, bucket rows and independently computed total rows for both periods. No historic data is manufactured.

Historical backfill, user-account activity linkage, tax refund reconciliation and comprehensive attribution remain outside these reports. New visitors with blocked tracking are not measured.

## Verification

- `npm run build` in API and admin.
- `node test/analytics.integration.cjs` in API, after building, against a disposable local PostgreSQL server on 127.0.0.1:55439 (override only the port with `ANALYTICS_TEST_PORT`), user `analytics_test`, database `postgres`. Tests create/drop their own schema and insert synthetic fixtures; never point them at a live database. Covers all eight report queries, tax totals, period boundaries, grouping, distinct/weighted totals, currencies, refunds, organization-scoped returning history, checkout deduplication, time windows, pending outcomes, free and later payments, authorization, exports, rerunnable migration, collector validation, ORM insertion/deduplication and pruning.
- `node test/analytics.cjs` in web checks session/visitor expiry, source classification, event context, deduplication, privacy signals and non-blocking tracking failures.

The public frontend uses the committed Node 22 setup and native optional dependencies. Validate with `npm ci --include=optional` and `npm run build` using that runtime.

Automatic setup verification: `node test/analytics-synchronize.integration.cjs` uses the same disposable local PostgreSQL connection as the report tests. It emulates the known pre-change schema, inserts sample user/organization/event/order records, then verifies that synchronization recreates the new columns, table and nine indexes without losing those records. Repeat synchronization is tested too. This does not establish that an uninspected production schema will have an identical synchronization plan.
